1. Local OS & AMD ROCm Driver Setup

While Windows has improved, Ubuntu 22.04 LTS or 24.04 LTS is mandatory for a stable, multi-GPU AMD setup. Linux memory allocation and tensor splitting algorithms are vastly superior here.

Installation Steps

After installing Ubuntu, you must install the proprietary AMD drivers and the ROCm (Radeon Open Compute) stack. Your 7800 XTs use the RDNA3 architecture (gfx1101), which is officially supported by modern ROCm.

# 1. Download the AMD installer
wget https://repo.radeon.com/amdgpu-install/6.1.2/ubuntu/jammy/amdgpu-install_6.1.20102-1_all.deb
sudo apt-get install ./amdgpu-install_6.1.20102-1_all.deb

# 2. Install the usecase for ROCm
sudo amdgpu-install --usecase=rocm
CRITICAL: Permissions
If you do not add your user to the video and render groups, Ollama will quietly fail to find your GPUs and will fallback to your CPU, running incredibly slowly. 
sudo usermod -a -G video $USER
sudo usermod -a -G render $USER
# You MUST reboot after this command

Verification

After rebooting, run the ROCm System Management Interface to verify both 7800 XTs are recognized:

rocm-smi

2. The Inference Stack (Battle of the Engines)

The "Engine" is the runtime that loads model weights and executes the tensor math. For your dual 7800 XT setup, you have three primary choices:

Engine Best For Advantage Disadvantage
Ollama Personal / Dev Zero config, model management. Opaque optimization, hard to tune.
vLLM Throughput / Production PagedAttention, Continuous Batching. Heavy dependencies, GGUF support is secondary.
llama.cpp Research / Max Perf Granular control over tensor splitting. Manual compilation, complex CLI.

Recommendation

Start with Ollama for convenience. If you find yourself waiting too long for long code files to process, switch to vLLM to take advantage of superior prefill (prompt eval) speeds.

3. Measuring Performance: Prefill vs. Decode

To understand if your software stack is "current" and healthy, you must measure two distinct stages of the LLM lifecycle:

Stage 1: Prefill (Prompt Evaluation)
The model reads your entire prompt (including all the code files you sent).
  • Unit: Tokens Per Second (t/s).
  • Impact: Determines "Time to First Token" (TTFT). Critical for agentic workflows where context can be 32k+ tokens.
  • Hardware Bottleneck: Compute bound (GPU Cores).
Stage 2: Decode (Token Generation)
The model generates the answer, one word at a time.
  • Unit: Tokens Per Second (t/s).
  • Impact: Determines how fast the model "types". A human reads at ~5-10 t/s.
  • Hardware Bottleneck: Memory Bandwidth (GDDR6 VRAM speed).
The 7800 XT Target: For a 32B model (Q4_K_M), you should aim for:
  • Prefill: >200 t/s
  • Decode: >15 t/s

3. Model Families & Quantization

A standard uncompressed (FP16) 32 Billion parameter model requires ~64GB of VRAM. To fit it into your 32GB budget, we use Quantization (compressing the model to 4-bit, 5-bit, or 6-bit precision, typically using the GGUF format).

A 32B model quantized to 6-bit (Q6_K) shrinks from 64GB down to ~24GB. This fits beautifully across your dual 7800 XTs, leaving 8GB of VRAM left over for your "Context Window" (the code files you send the agent).

The Heavyweights

  • Qwen 2.5 Coder 32B: The undisputed king of open-weight coding models. Exceptionally strong in typed languages like Golang and Rust. This is your primary daily driver for agentic coding. Run via: ollama run qwen2.5-coder:32b
  • Llama 3.1 8B: Blazing fast. Excellent for quick bash scripting, formatting text, or "router" agents. Uses < 6GB of VRAM.
  • Gemma 2 27B: Google's dense powerhouse. Incredible general reasoning and logic skills, fits comfortably in your VRAM limit.
The 70B Trap: Even heavily quantized, a 70B model requires ~40GB of VRAM. Your system will "spill" the remaining 8GB into your slow DDR4 system RAM, causing generation speed to drop off a cliff (e.g., from 25 tokens/sec to 3 tokens/sec). Stick to ~32B models.

4. Benchmarks & Local Evaluation

Do not rely on Twitter hype. Use specific, empirical benchmarks to evaluate new models.

  • The Aider LLM Leaderboard: Tests how well a model can read an existing, complex codebase, understand it, and surgically edit specific lines without breaking the file. The most important metric for agentic coding.
  • SWE-bench: Tests a model's ability to autonomously navigate a massive repository, find a bug based on a GitHub issue, and generate a patch.
  • LMSYS Chatbot Arena: A blind A/B testing leaderboard based on Elo ratings. Good for assessing "vibes" and instruction-following.

Local Verification

When you download a new model, test its Context Degradation (the "Needle in a Haystack" test). Dump 10 massive Golang files into the prompt and ask a specific question about a buried variable. If it hallucinates, the model's context window cannot handle agentic workloads.

6. Hooking up Agentic Workloads

Agentic tools (like CLAW, Aider, and Cline) are typically hardcoded to look for the OpenAI API. You "trick" them into talking to your local GPUs by overriding two environment variables:

export OPENAI_API_BASE="http://localhost:11434/v1"
        export OPENAI_API_KEY="dummy-key-ollama"

The Tools

  • CLAW / Gemini CLI: Terminal-based, multi-step execution. Excellent for massive refactoring loops and running integration tests autonomously.
  • Aider: A terminal pair programmer that tracks your git repository and surgically edits your files.
  • Cline / Claude Dev: A VSCode extension that lives in your sidebar, reads open files, and proposes diffs visually.
Context Window Blowout: Every 8,000 tokens of context requires roughly 1GB of VRAM to hold in memory. If your agent tries to send 100,000 tokens of context alongside a 24GB model, your 32GB VRAM will overflow. Solution: Use .aiderignore or .clineignore files to hide massive directories (like node_modules) from the agents.

8. Glossary of Terms

Dense Models
A standard model architecture (like Llama 3 or Gemma 2) where 100% of the parameters are used to calculate every single token. These are generally more stable and easier to train but require more compute per token as they scale up.
Mixture of Experts (MoE)
An architecture (like Mixtral or DeepSeek-V3) where only a small subset of the total parameters (the "Experts") are active for any given token. This allows for massive total parameter counts while maintaining fast inference speeds.
Effective Parameters
In the context of MoE models, this is the number of parameters actually used per token. For example, a 141B parameter MoE model might only use 39B "effective" parameters per forward pass, meaning it runs as fast as a 39B dense model while having the knowledge of a much larger one.
Temperature
A hyperparameter that controls the "randomness" or "creativity" of the output.
  • 0.0 (Deterministic): Best for coding and math. The model always picks the most likely next token.
  • 0.7 - 1.0 (Creative): Best for creative writing or brainstorming.
Top-P (Nucleus Sampling)
A companion to Temperature. It limits the model's choices to a subset of tokens whose cumulative probability reaches a certain threshold (e.g., 0.9). This helps cut off the "long tail" of low-probability, nonsensical words.
Tokens
The atomic units of an LLM. A token is roughly 3/4 of a word. When you see TPS (Tokens Per Second), it's the speed at which the model is "thinking." For coding, you generally want at least 15-20 TPS for a fluid experience.
KV Cache (Key-Value Cache)
This is where your VRAM goes when you send a large context. It stores the mathematical representations of the conversation history so the model doesn't have to re-calculate everything for every new word. This is why "Context Window Blowout" happens—more context = more KV Cache = more VRAM usage.
System Prompt
The high-level instructions given to a model before the conversation starts (e.g., "You are an expert Rust engineer"). In agentic coding, the system prompt is what gives the model the "personality" and rules it needs to edit files and run tests safely.
Context Window
The "short-term memory" of the model. It defines how many tokens (roughly words or code fragments) the model can look at at once. For agentic coding, a large context window is vital for reading multiple files simultaneously.

9. The Bi-Weekly Maintenance Loop

The open-weight AI space moves incredibly fast. To maintain your edge and keep your Dual 7800 XT rig at peak performance, follow this simple 2-hour loop every few weeks.

Step 1: Update the OS & ROCm Drivers

AMD releases frequent ROCm patches that improve stability and tensor splitting performance.

sudo apt update && sudo apt upgrade -y
        # Check if rocm-smi still works
        rocm-smi

Step 2: Update the Engines

Ollama and vLLM are in rapid development. New versions often include "Flash Attention" optimizations for RDNA3.

curl -fsSL https://ollama.com/install.sh | sh

Step 3: Run Benchmarks

Use the benchmark_ollama.py script to verify that your Tokens Per Second (TPS) hasn't dropped. If it has, check for background processes or driver regressions.

Step 4: Audit Your RSS Feeds

Check your curated feeds for new model releases. Look for "Qwen 2.5 Coder" successors or new "DeepSeek" quants.

  • r/LocalLLaMA: Look for "New Quant" or "GGUF" tags.
  • HuggingFace: Watch bartowski for the latest RDNA3-optimized quants.
